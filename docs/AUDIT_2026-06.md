## Decisions / Scope

- **Lenses (5):** `[CODE]` Code & architecture · `[BALANCE]` Game design & balance · `[LORE]` Lore & narrative · `[DOCS]` Docs & project hygiene · `[DX]` Maintainability / optimization / future-proofing.
- **Action mode:** Read-only. Nothing is fixed; defects are logged with `file:line` + suggested remediation.
- **Data depth:** Full per-entry validation of every data table.
- **Severity:** `CRITICAL` (data loss / save corruption / economy break / crash) · `HIGH` (wrong behavior players will hit) · `MEDIUM` (incorrect but recoverable / minor balance) · `LOW` (cosmetic / inconsistency) · `OBS` (DX / refactor opportunity).

### Headline: the StatusEffect schism (AUD-028, HIGH)
There are **two parallel StatusEffect systems** that don't agree:

| | `Character.ts` (persisted on character) | `StatusEffect.ts` (combat engine logic) |
|---|---|---|
| Interface | `{id: StatusEffectId, name, duration, damagePerTurn?, statModifier?: Partial<Record<StatName,number>>, description}` | `{id: string, type: StatusEffectType, name, description, duration, maxDuration, percentDamage?, preventsHealing?, skipTurnChance?, stacks?, …}` |
| ID set | poison, bleed, burn, freeze, stun, **fear, silence, paralysis**, blind, curse | poison, burn, freeze, stun, blind, bleed, **weaken, slow, regen**, curse |

Only 7 of 10 IDs overlap. The shapes are structurally incompatible. **`Monster.ts` actively mixes both**: it imports `StatusEffectId` (Character set) for `MonsterSuffix.statusEffect`/`Monster.statusEffects`/`MonsterAbility.effectId`, but its `STATUS_EFFECT_CR_WEIGHTS` table (line 346) is keyed with the `StatusEffect.ts` vocabulary (`weaken`/`slow` present; `fear`/`silence`/`paralysis` absent). Consequences: a suffix applying `'fear'` contributes **0** to CR (no weight entry); `weaken`/`slow` CR weights are **dead** (no `StatusEffectId` can reference them); and BUG-040's "which StatusEffect type?" confusion is structural, not incidental. PROGRESS.md's "official 10" matches `StatusEffect.ts`, making `Character.ts`'s `fear`/`silence`/`paralysis` the orphans. **This needs a single unified status model** — traced through combat store (S4) and combat screen (S10).

### Headline: the Paragon title bug (AUD-049, HIGH)
`Behavement.ts:293` `getStatAdjective(stat1, stat2)` does `[stat1, stat2].sort()` (alphabetical) then looks up `STAT_ADJECTIVE_MAP`. But the map's keys aren't alphabetised — **14 of 28 are reversed**: `STR_END`, `STR_AGI`, `STR_INT`, `STR_PER`, `STR_CHA`, `STR_LCK`, `END_AGI`, `END_CHA`, `INT_CHA`, `WIS_PER`, `WIS_CHA`, `WIS_LCK`, `PER_CHA`, `PER_LCK`. For any of those stat pairs the sorted key (`AGI_STR`, `CHA_INT`, …) misses → `?? 'Iron'`. So **half of all Level-10 Paragon titles silently get "Iron"** instead of the intended adjective (a STR/AGI player who should be "Savage" reads "Iron"; STR/END players coincidentally still get "Iron", masking it). The Denatus title is the documented climax of the whole soul system — and it's 50% wrong. Fix: either alphabetise the map keys or drop the sort and require canonical key order. Trivial fix, high player impact, fully verifiable.

**Related design gap — AUD-065 (MEDIUM, player agency):** even once AUD-049's key bug is fixed, the title generator chooses the player's identity *for* them. `generateParagonTitle` receives a `topStats` pair the caller has already reduced from 8 stats, and ties are broken arbitrarily — alphabetical stat order for the adjective, and `getDominantVector` defaulting to the first-encountered vector (`COMBAT_PHYSICAL`) for the noun. The pathological case is the player who maxes *everything* (all-SSS): they did the most work and get the least say — the game hands them, say, "AGI/CHA → Dashing" purely because A and C sort first, possibly a build identity they never expressed. The endgame reward should *reward effort with choice*: when multiple stats/vectors are tied (or within a small margin), let the player pick which two stats and which vector crown their title, rather than letting `.sort()` decide. ### AUD-082 root cause found (AUD-087)
There are **two stat-growth systems** in the character store:
1. `addStatProficiency` — proficiency accrues against `getProficiencyThreshold = 100*(gradeIdx+1)`, which **does** make each grade cost more (I→H = 100, A→S = 900, SS→SSS = 1100), and each grade-up grants +100 points.
2. `commitExcelia` — the Falna/Blessing-Rite path — adds pending excelia as **flat raw points** ("1 excelia = 1 point", line 401), with grade derived purely from the point band.

These disagree. The DanMachi design routes combat → `addPendingExcelia` → (Blessing Rite) → `commitExcelia`, i.e. the **flat** path. If that's the live path (confirm combat doesn't call `addStatProficiency` — S10), then the increasing-cost curve is **dead code**, and reaching SSS is just "accumulate 980 flat points," where the narrow top bands (S=50/SS=30/SSS=20, AUD-082) make A→SSS *cheaper* than the first grade. So the mechanism the user wants (SSS = real grind) **half-exists already** in `addStatProficiency` but is bypassed. The fix for AUD-082 is therefore as much "route growth through an increasing-cost curve" as "widen the top bands."

The codebase keeps *adding* a second mechanism instead of replacing the first — so the live path and the dead path coexist, and which is which requires runtime tracing (S10).
3. **Unobtainable/locked content is a quiet theme** (AUD-085 sacred metrics, AUD-086 deities, AUD-084 unusable armor, AUD-049 wrong titles). Individually small; together they suggest a layer of designed content that the wiring doesn't actually deliver to players.

### Headline — AUD-090 (HIGH): three favor→multiplier tables, one with a 0×
`useDeityStore.FAVOR_STATUS` (7 tiers, **Abandoned = 0×**, Favoured Child = 2.0×) ≠ `Deity.ts FAVOR_TIERS` (6 tiers, Abandoned = 0.5×, Chosen = 1.5×, the one character HP/combat actually uses) ≠ PlayerSnapshot's 3 buckets (AUD-054). `useDeityStore.getBlessingMultiplier()` returns numbers that don't match what's applied; its `0×` would zero a character if ever wired to stats. ### Combat (`useCombatStore`) — the best file in the codebase, with one real gap
- **Resolutions:** weapon triangle **is** wired with armor normalization (AUD-039 resolved); `Combat.flee`/`Loot` GameConstants **are** imported here (so AUD-068 is live/dead *mix*, not all-dead); status effects use the `StatusEffect.ts` vocabulary on ephemeral arrays (AUD-028 doesn't crash combat — but the persisted `character.statusEffects` uses the other vocabulary, so a shrine status won't be cured in combat).

### Doesn't-feel-fine (S4 overall)
1. **"Two sources of truth" is now the dominant defect class in the codebase.** Favor (×3-4: AUD-033/034/054/090), status vocabulary (AUD-028), volume (AUD-104), blacksmith reputation (AUD-096), learned-skill type (AUD-052), domain union (AUD-059), growth path (AUD-087), Garm NPC (AUD-063). The pattern is identical every time: a second representation was added without retiring the first, and they drift. This is the single highest-leverage architectural cleanup — more than any individual bug.

The logic is right; the question is whether it's invoked. S9/S10 (the screens) will resolve most of them.
3. **Severity discipline matters: I revised 3 findings down after reading actual flow (AUD-066, AUD-030, AUD-033) and 1 up (AUD-090).** The static/doc-based passes (S1-S3) systematically over-flagged; the store reads corrected them. Worth remembering when triaging the table — `file:line` claims are verified, but "what calls this" is still pending for the screen-dependent items.
